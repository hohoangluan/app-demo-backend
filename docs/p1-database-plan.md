# P1 Database Plan

Kế hoạch độc lập cho database foundation của P1. Phạm vi file này chỉ gồm
PostgreSQL, SQLAlchemy, Alembic, transaction boundaries và integration tests.
Không định nghĩa lại Public/Internal contract và không triển khai worker loop.

Nguồn:

- `architeture.md` mục 6-9 và 15-16.
- `claude.md` mục 2-6.
- [`CONTRACT_DECISIONS.md`](../CONTRACT_DECISIONS.md), với `D-01` đến `D-13`
  tương ứng mục 1 đến 13.
- [`contracts/contract-matrix.md`](../contracts/contract-matrix.md) cho mapping 9
  operation/action và timeout.

## Nguyên tắc không được phá vỡ

- PostgreSQL là database test bắt buộc; không thay locking, JSONB, migration hay
  race tests bằng SQLite.
- Hướng phụ thuộc: `api -> service -> repository -> PostgreSQL`; worker chỉ gọi
  service/repository/adapter và không import router.
- Pydantic schema tách SQLAlchemy model.
- Alembic là nơi duy nhất tạo/thay đổi schema; application startup không gọi
  `create_all`.
- Persist operation thành công trước khi trả `202`.
- Delivery/callback là at-least-once; claim commit trước network I/O; terminal
  public state immutable.
- Các quyết định contract đang mở chỉ được tham chiếu, không được chốt trong kế
  hoạch database này.

## Kiểu và enum logic

P1 dùng PostgreSQL `varchar` + named `CHECK` cho enum logic, thay vì native
PostgreSQL ENUM. Cách này giữ migration đơn giản nhưng vẫn khóa tập giá trị ở DB.
Python dùng `StrEnum`; SQLAlchemy persist `.value` chính xác.

| Logical enum | Giá trị chính xác |
|---|---|
| `device_platform` | `android` |
| `device_status` | `active`, `inactive`, `revoked` |
| `operation_name` / `action_name` | `ride_quote`, `ride_confirm`, `music_play`, `music_stop`, `music_volume`, `navigation_start`, `navigation_stop`, `emergency_call`, `contact_call` |
| `request_state` | `processing`, `succeeded`, `failed`, `timed_out` |
| `delivery_state` | `received`, `sending`, `retry`, `sent`, `failed`, `report_received`, `report_timeout` |
| `callback_state` | `not_required`, `pending`, `sending`, `retry`, `delivered`, `dead_letter` |

| `client_id` | `varchar` | No | None | Authenticated Public principal / ownership key |

| `error` | `jsonb` | Yes | SQL `NULL` | `{code,message,details}` only for failed/timed_out operation |

| `callback_state` | `varchar(24)` | No | Supplied by service | `not_required` or callback lifecycle state |
| `callback_attempts` | `integer` | No | `0` | Incremented when a callback claim is created |
| `next_callback_at` | `timestamptz` | Yes | SQL `NULL` | Due time for callback `pending`/`retry` |
| `callback_locked_until` | `timestamptz` | Yes | SQL `NULL` | Callback lease/fencing value |
| `report_payload_hash` | `char(64)` | Yes | SQL `NULL` | Accepted report hash for deduplication |
| `created_at` | `timestamptz` | No | DB `now()` | Original acceptance time |
| `updated_at` | `timestamptz` | No | DB `now()` | Updated explicitly in every mutation |
| `expires_at` | `timestamptz` | No | None | `created_at +` action timeout |
| `completed_at` | `timestamptz` | Yes | SQL `NULL` | First and only terminal transition time |

### Constraints

| Name | Definition |
|---|---|
| `pk_operations` | Primary key (`request_id`) |
| `ck_operations_operation` | `operation` in the exact 9-value operation set |
| `ck_operations_action` | `action` in the exact 9-value action set |
| `ck_operations_mapping` | `operation = action` for the current fixed mapping |
| `ck_operations_request_state` | `request_state IN ('processing','succeeded','failed','timed_out')` |
| `ck_operations_delivery_state` | `delivery_state IN ('received','sending','retry','sent','failed','report_received','report_timeout')` |
| `ck_operations_callback_state` | `callback_state IN ('not_required','pending','sending','retry','delivered','dead_letter')` |
| `ck_operations_delivery_attempts` | `delivery_attempts >= 0` |
| `ck_operations_callback_attempts` | `callback_attempts >= 0` |
| `ck_operations_request_fingerprint` | `length(request_fingerprint) = 64` |
| `ck_operations_report_payload_hash` | `report_payload_hash IS NULL OR length(report_payload_hash) = 64` |
| `ck_operations_terminal_payload` | Processing requires SQL-null result/error/completed_at; succeeded requires non-null result, null error, non-null completed_at; failed/timed_out require null result, non-null error, non-null completed_at |

`jsonb` JSON literal `null` không được dùng thay SQL `NULL`; repository phải bind
Python `None` thành SQL `NULL`. Result/error shape vẫn được validate bằng
action-specific Pydantic schema ở service boundary; DB không tự suy ra business
schema. Exact Internal error policy phụ thuộc `D-04`, validation/canonicalization
phụ thuộc `D-07`, emergency result phụ thuộc `D-08`.

|---|---|
| `ix_operations_delivery_due` | (`request_state`, `delivery_state`, `next_delivery_at`) for due delivery claims |
| `ix_operations_timeout_due` | (`request_state`, `expires_at`) for timeout scan |

## SQLAlchemy boundaries

### Models

- SQLAlchemy 2 declarative models chỉ mô tả column, relationship-free schema,
  named constraints và indexes.
- Dùng `Mapped[...]`, `mapped_column`, PostgreSQL `UUID`/`JSONB`, và
  `DateTime(timezone=True)`.
- `devices.device_id` và `operations.device_id` không tạo ORM relationship.
- Python `StrEnum` là type-safe value set; DB vẫn dùng varchar + checks ở trên.
- Model không chứa HTTP error mapping, FCM call, callback call, endpoint mapping
  decision hoặc state-transition orchestration.

### Repositories

- `DeviceRepository`: upsert/rotate theo policy đã chốt, resolve latest active,
  update last-seen/status; không giải mã/gửi FCM token ngoài adapter boundary.
- `OperationRepository`: atomic insert, lookup by request/client, row lock,
  conditional terminal update, delivery/callback claim and fenced completion.
- Repository trả typed records/outcomes; không trả FastAPI response hoặc chọn
  Public error code.
- Mỗi public use case/service call sở hữu session/transaction; repository không
  commit ngầm giữa các bước của cùng use case.

### Services

- `OperationService` sở hữu endpoint-to-action mapping, fingerprint,
  idempotency outcome và Public state transition.
- `ReportService` sở hữu auth ownership/action/result validation, report hash,
  duplicate classification và terminal transition.
- `DeviceService` sở hữu enrollment/revocation policy sau khi `D-05` được chốt.
- `TARGET_UNAVAILABLE` transition chưa được cố định cho tới `D-03`; report
  conflict/late-report outcome chưa cố định cho tới `D-09`.

## Alembic boundaries

1. Cấu hình Alembic dùng application metadata nhưng không import FastAPI app hay
   khởi động worker.
2. Migration đầu tiên tạo `devices`, sau đó `operations`, named checks và exact
   indexes ở trên. `downgrade` drop `operations` trước `devices`.
3. Không seed token/device/operation trong schema migration; seed/reset là script
   riêng ở phase sau.
4. Không dùng database trigger cho `updated_at`, terminal immutability hoặc retry;
   service/repository thực hiện explicit update có test.
5. Không dùng `Base.metadata.create_all` trong runtime hoặc test integration;
   test database sạch phải chạy `alembic upgrade head`.
6. Review generated SQL/diff trước commit; migration đã commit không bị sửa sau
   khi có migration kế tiếp.

## Transaction design

### A. Accept request và idempotency

Fingerprint theo blueprint:

```text
SHA-256(client_id + method + path + canonical_validated_body)
```

Canonical validated body bao gồm `request_id` và `user_id`; key ordering và JSON
encoding phải deterministic. Chi tiết reject/normalize extra fields và
address/coordinates lần lượt phụ thuộc `D-07` và `D-11`.

Một transaction, isolation mặc định PostgreSQL `READ COMMITTED`:

1. Router auth/validate; service map method/path thành operation/action cố định,
   tính fingerprint và timeout.
2. Repository chạy `INSERT ... ON CONFLICT (request_id) DO NOTHING RETURNING` với
   state `processing/received`, `next_delivery_at = created_at` và `expires_at`.
3. Nếu insert thành công: commit rồi mới trả `202`.
4. Nếu conflict: đọc existing row theo `request_id` trong cùng transaction.
5. Cùng `client_id` và fingerprint: trả original operation, không update và không
   tạo delivery thứ hai.
6. Khác fingerprint/client: service map thành `409 REQUEST_ID_CONFLICT` theo
   Public contract.

`accepted_at` khi duplicate phải chờ `D-10`; storage luôn giữ `created_at` gốc.
Ownership response cho status phụ thuộc `D-06`, nhưng lookup luôn filter/verify
`client_id`.

### B. Delivery claim/lease

Repository primitive chuẩn bị cho P2; network send không thuộc P1:

1. Trong transaction ngắn, chọn operation `processing` theo một trong hai nhánh:
   - `delivery_state IN ('received','retry') AND next_delivery_at <= now()`; hoặc
   - `delivery_state = 'sending' AND delivery_locked_until <= now()`.
2. `ORDER BY next_delivery_at NULLS LAST, created_at`,
   `FOR UPDATE SKIP LOCKED`, giới hạn batch.
3. Resolve latest active device; update row thành `sending`, set `device_id`,
   tăng `delivery_attempts`, set `delivery_locked_until = lease_until`; commit.
4. FCM call xảy ra ngoài transaction.
5. Outcome transaction dùng conditional update với cả `request_id`,
   `delivery_state='sending'` và exact `delivery_locked_until=lease_until`.
   `lease_until` là fencing value: stale worker update zero rows và không được
   ghi đè owner mới.
6. Success -> `sent`; transient -> `retry` + `next_delivery_at`; permanent ->
   `failed` và conditional terminal transition theo policy đã chốt. Clear lease
   trong mọi accepted outcome.

Device unavailable/permanent failure mapping bị chặn bởi `D-03`; transaction
primitive không tự chọn sync/async Public behavior.

### C. Callback claim/lease

Repository primitive chuẩn bị cho P2:

1. Chỉ claim terminal operation có callback `pending/retry` đến hạn hoặc
   `sending` với expired lease.
2. Claim bằng `FOR UPDATE SKIP LOCKED`; set `sending`, tăng attempt và set exact
   `callback_locked_until`; commit.
3. HTTP callback ngoài transaction.
4. Persist outcome bằng fenced conditional update theo exact lease value:
   `delivered`, `retry + next_callback_at`, hoặc `dead_letter`.
5. Callback outcome không bao giờ thay đổi terminal `request_state`.

Retry classification/body phụ thuộc `D-02`; representation phụ thuộc `D-12`.

### D. Device report và timeout race

1. Report service bắt đầu transaction và `SELECT ... FOR UPDATE` operation theo
   `request_id`.
2. Validate token ownership, user/device/action và action-specific result/error.
3. Hash canonical report. Exact accepted hash duplicate trả idempotent success;
   conflicting/late behavior phụ thuộc `D-09`.
4. Chỉ `processing` được chuyển terminal. Success report set succeeded/result;
   failure report set failed/error; cả hai set `completed_at`,
   `delivery_state=report_received`, report hash và callback scheduling.
5. Timeout dùng conditional update
   `WHERE request_state='processing' AND expires_at <= now()` để set
   `timed_out`, `delivery_state=report_timeout`, internal timeout reason
   `REPORT_TIMEOUT` theo blueprint (`D-13`),
   `completed_at` và callback scheduling.
6. Row lock/conditional predicate bảo đảm report và timeout chỉ có một winner;
   terminal state không được update lần hai.

`D-13` chưa chốt việc công bố `REPORT_TIMEOUT` qua Public API. Repository có thể
persist/test reason này theo internal blueprint, nhưng Public OpenAPI, example và
consumer contract test không được coi nó là stable code trước khi được duyệt.

## PostgreSQL integration test matrix

Mỗi test dùng database riêng/schema sạch, chạy migration, transaction hữu hạn và
không dùng arbitrary `sleep`.

| ID | Area | Scenario | Assertion chính | Decision dependency |
|---|---|---|---|---|
| `PG-01` | Migration | Upgrade empty DB to head | Hai table, exact columns/checks/indexes tồn tại | None |
| `PG-02` | Migration | Downgrade head to base rồi upgrade lại | Drop/create đúng thứ tự, không drift | None |
| `PG-03` | Devices | Hai row cùng `device_id` | Một insert fail unique; transaction khác không hỏng | None |
| `PG-04` | Devices | Active/inactive/revoked với `last_seen_at` khác nhau | Resolver chỉ lấy active mới nhất | `D-05` chỉ ảnh hưởng one-active enforcement |
| `PG-05` | Devices | Invalid platform/status/hash length | Named DB checks reject | None |
| `PG-06` | Operation | Valid row + JSONB params round-trip | UUID/timezone/JSONB giữ đúng type/value | `D-07` |
| `PG-07` | Operation | Invalid enum/mapping/attempt/hash | Named checks reject từng case | None |
| `PG-08` | Terminal payload | Mỗi request state với result/error/completed_at hợp lệ và sai | Coherence check chấp nhận/reject đúng | `D-07`, `D-08` |

| `PG-10` | Idempotency | Sequential same ID + different fingerprint | Một row; repository outcome conflict | None |
| `PG-11` | Idempotency race | Hai connection insert same ID/same fingerprint đồng thời | Một insert winner; loser đọc original; không duplicate | None |

| `PG-13` | Delivery claim | Hai claimers cùng due batch | `SKIP LOCKED` trả disjoint request IDs | None |
| `PG-14` | Delivery lease | Claimed `sending` chưa hết lease | Claimer khác không lấy row | None |

thứ tự lock; mọi wait có timeout hữu hạn. Không dùng shared mutable fixture hoặc
database chứa dữ liệu thật.

## Exit criteria

- Initial migration tái tạo exact schema từ database sạch và downgrade sạch.
- SQLAlchemy metadata không drift với Alembic head.
- Idempotent insert an toàn khi concurrent; conflicting fingerprint không tạo row
  thứ hai.
- Delivery/callback claims disjoint, recover expired lease và reject stale worker
  outcome bằng fencing condition.
- Report/timeout race chỉ tạo một immutable terminal transition.
- PostgreSQL integration matrix áp dụng được đã pass; không có SQLite substitute.
- Không có token/location/contact raw trong fixture, assertion output hoặc log.
- Mọi hành vi phụ thuộc `D-01` đến `D-13` vẫn được ghi rõ là unresolved cho tới
  khi có entry trong Decisions log.
